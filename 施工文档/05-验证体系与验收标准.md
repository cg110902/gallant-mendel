# 验证体系与验收标准
## 从“能运行”到“可相信”

---

## 1. 验证目标

验证不负责证明作品“文学上绝对优秀”。验证负责证明：

1. 系统遵守了已声明的硬规则。
2. 状态和正文没有发生未登记的矛盾。
3. Agent 没有越权写入。
4. 失败没有静默污染后续章节。
5. 阈值和评分器经过样本标定。
6. 质量指标不会因为篇幅变长而虚假变好。
7. 任何“通过”都能找到外部证据。

---

## 2. 验证层级

```text
L0 文件/JSON/YAML/Schema
L1 确定性状态与不变量
L2 事件重放、快照、回滚、幂等
L3 任务/Artifact/权限契约
L4 语义一致性与证据链
L5 文风、重复、节奏、商业指标
L6 端到端章节与长篇压测
L7 人工评审与发布门
```

低层失败必须阻断高层，不允许用文学评分掩盖状态错误。

---

## 3. 测试类型

### 3.1 单元测试

覆盖：

- ID
- hash
- 原子写入
- 时间窗口
- 状态转换
- 义务生命周期
- 知识集合
- 事件重放
- diff
- 退出码

### 3.2 契约测试

验证各模块输入输出：

```text
Outline Compiler → Initial State
Context Builder → ContextPack
Writer → ArtifactBundle
Extractor → Candidate Delta
Reconciler → Events
Auditor → Evidence Report
Committer → Published State
```

### 3.3 Golden Tests

固定输入和预期输出：

- 一个最小完整大纲
- 一个倒叙案例
- 一个角色知识泄漏案例
- 一个伏笔履约案例
- 一个涌现实体案例
- 一个回滚后重产案例

Golden 文件必须版本化，改变结果必须写 ADR。

### 3.4 Mutation Tests

变异器生成理论上应该被拦截的内容：

```text
KillThenAct
GhostCharacter
TimeReversal
KnowledgeLeak
PersonaDrift
HookRemoval
ForeshadowGhost
PowerJump
TropeRepeat
WordCountCheat
```

每个变异样本必须有：

- mutator_id
- 原始正确版本
- 破坏版本
- 预期命中的闸门
- 实际检测结果
- evidence

### 3.5 Soak Tests

阶段：

```text
3 章：闭环 smoke
10 章：状态增长
30 章：中断/恢复/审计
100 章：性能和投影
```

首期不追求百万字实产，但必须验证线性增长和无静默丢失。

## 4. Oracle 体系

### 4.1 确定性 Oracle

优先使用代码验证：

- 字数
- ID
- 时间排序
- 关系存在
- 资源余额
- 状态机合法性
- 证据区间
- 禁止词/实体
- 事件 hash

### 4.2 离线写手 Oracle

离线写手不是生产写手，而是闸门测试 Oracle：

- 按契约生成格式稳定的正确文本
- 有意生成边界情况
- 不依赖外部 API
- 用于验证“好样本能通过”

### 4.3 LLM Judge

只用于代码难以判定的维度，并必须：

- 独立上下文
- 版本化 rubric
- 证据引用
- 双向 pairwise 时交换顺序
- 记录模型家族
- 以人工样本测 Cohen’s kappa 或其他一致性
- 不让写手自评自己的正文

Judge 只能输出建议，不直接修改权威状态。

## 5. 指标体系

### 5.1 硬指标

```text
hard_violation_count
unregistered_entity_count
knowledge_leak_count
temporal_error_count
state_replay_mismatch_count
evidence_missing_count
silent_write_count
```

任何 hard 指标大于 0，章节不能 commit。

### 5.2 一致性指标

```text
CED                  固定长度窗口的一致性错误密度
obligation_coverage  义务按期触达/履约比例
fact_reconciliation  意图/实况平账成功率
reader_tension       R/C/T 集合曲线
state_drift          状态漂移率
```

### 5.3 文风与平台指标

只能作为软指标：

- burstiness
- 句长方差
- 重复 n-gram
- 章间相似度
- 风格词密度
- 标点熵
- 信息引入率
- AI-style risk

不得把单一 burstiness 阈值当作“AI 生成证明”。阈值必须在自己的语料上标定。

## 6. 风险触发器

以下任一条件触发增强审计：

```text
章节位于整书中部
高 token entropy
开放义务密度高
主角/反派身份发生变化
时间跳跃或倒叙
新增核心实体
多个剧情线交汇
卷末/高潮
候选正文之间分歧大
近期连续出现审计失败
```

增强动作：

```text
增加 ContextPack 证据
增加全局通读审查
运行局部 Best-of-N
增加角色/读者知识检查
运行共现错误类型审查
要求人工确认
```

---

## 7. 阈值治理

阈值文件必须包含：

```yaml
metric: repetition_rate
value: 0.18
severity: warning
calibrated_at: 2026-09-29
sample_size: 120
distribution:
  p50: 0.07
  p90: 0.16
  p99: 0.24
rationale: ...
owner: quality
expires_at: 2026-12-29
```

没有 `calibrated_at`、`sample_size`、`distribution` 和 `rationale` 的阈值不得进入生产硬门禁。

## 8. 四级发布门

### Gate 0：输入门

- Outline Package 通过 schema。
- 无硬引用错误。
- 生产任务可生成。

### Gate 1：候选门

- ArtifactBundle 可解析。
- 正文、抽取和证据文件存在。
- Writer 没有越权写入。

### Gate 2：状态门

- Reconcile 成功。
- 所有硬不变量通过。
- 义务、知识、时间状态合法。

### Gate 3：发布门

- 审计报告存在。
- 无未决 P0/P1 问题。
- 人工断点已处理。
- snapshot 已创建。
- commit 事件已追加。

## 9. 验收样例

### 例一：死者行动

输入：角色在第 20 章死亡，第 21 章出现行动。

预期：

- `hard_violation_count += 1`
- 输出死亡事件和行动证据
- 退出码 3
- 不更新权威状态

### 例二：知识泄漏

输入：角色尚未见过某秘密，却在 POV 内准确说出秘密。

预期：

- knowledge audit 命中
- evidence 指向泄漏句
- 退出码 3 或 4

### 例三：正文涌现实体

输入：写手引入大纲未注册的店名。

预期：

- 进入 candidate entity
- 不自动成为 canonical object
- 生成人工确认任务

### 例四：审计后修复变差

输入：补丁后违规数由 1 变 2。

预期：

- 补丁被拒绝
- 保留原版本和补丁版本
- 记录 patch regression
- 不接受“最新版本”

## 10. 阶段完成的证据格式

每个阶段根目录生成：

```text
verification/<milestone>/
├── test-run.json
├── command-log.txt
├── metrics.json
├── failures.json
├── evidence-index.json
├── human-signoff.md
└── decision.md
```

阶段完成语句必须能写成：

```text
M1 完成，因为：
- 运行了哪些命令
- 通过了哪些测试
- 失败样本是什么
- 已知限制是什么
- 谁批准继续
```

不得使用：“看起来没问题”“模型说已完成”。
