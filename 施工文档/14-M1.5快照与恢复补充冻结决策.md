# M1.5 快照与恢复补充冻结决策
## Snapshot and Restore v1

- 状态：已接受
- 日期：2026-09-29
- 影响范围：M1.5 Snapshot、restore 与 M1 总验收
- 性质：对快照目录、manifest 和非破坏恢复语义的向前兼容补充

## 1. 快照不是新权威

- 事件日志仍是权威历史。
- Snapshot 是某一 branch lineage、对应 SQLite 派生投影和选定文件产物的可验证恢复包。
- 创建基础设施快照本身不追加 `snapshot.created` 事件，避免文件发布与事件追加之间出现无法原子提交的双写。后续生产提交阶段可以在快照发布成功后记录业务级 `snapshot.created` 事件。
- Snapshot 不允许成为唯一存在的历史副本。

## 2. 路径和 ID

```text
workspace/<book>/snapshots/snapshot_<32位小写UUID4>/
├── manifest.json
├── artifacts.json
├── ledger/events.jsonl
├── state/state.db
└── artifacts/files/<原书内相对路径>   # 可选
```

快照先在同目录隐藏临时目录中完成，全部校验后通过原子目录 rename 发布。

## 3. Manifest v1

`manifest.json` 固定包含：

```text
schema_version = snapshot.v1
snapshot_id
book_id
branch_id
label
created_at
head_event_id
lineage_event_count
projection_state_hash
files
```

`files` 至少记录：

- `ledger/events.jsonl`
- `state/state.db`
- `artifacts.json`

每项包含相对路径、角色、字节数和 `sha256:<64位小写十六进制>`。

`artifacts.json` 固定包含 `schema_version = snapshot-artifacts.v1` 和选定书内文件的来源相对路径、快照相对路径、字节数与 hash。M1.5 允许空清单。

## 4. 一致性

创建快照前必须：

1. 验证 EventLog 和所有 branch heads；
2. 验证目标 branch lineage；
3. 验证 SQLite 投影与完整 lineage 一致；
4. 使用 `sqlite3.Connection.backup()` 创建一致数据库副本；
5. 校验副本的 `integrity_check`、`foreign_key_check`、branch、event head、event count 和逻辑 state hash；
6. 校验事件副本最后一行、head 和数量；
7. fsync 文件和目录后发布。

## 5. Artifact 边界

- 只接受位于书籍根目录内的普通文件。
- 拒绝目录、符号链接、越界路径、重复路径和运行中的 SQLite 文件。
- 默认不自动收集任何 artifact；调用方必须显式列出。
- Snapshot 内保存实际字节，不只保存路径声明。

## 6. 验证

快照验证必须是只读的，不创建 lock、head 或临时业务文件。验证内容：

- manifest 顶层字段严格；
- snapshot ID、时间、branch、hash 格式合法；
- 只允许 manifest 声明的文件；
- 所有文件 hash 和字节数匹配；
- 事件 lineage 连续且 head/count 匹配；
- SQLite 完整且 metadata/state hash 匹配；
- artifact manifest 与实际文件集合匹配。

任何不匹配都拒绝恢复。

## 7. 非破坏 Restore

M1.5 restore 只允许恢复到**不存在的新书目录**：

```text
snapshot validate
→ 在目标同级隐藏临时目录组装
→ 恢复 lineage events.jsonl
→ 从事件重建 branch heads
→ 恢复 state.db
→ 恢复 artifacts
→ 验证 EventLog 与 ProjectionStore
→ 原子 rename 发布目标目录
```

禁止覆盖现有书目录，禁止删除现有事件，禁止原地回退。已有书的非破坏分支回滚留给 M7。

## 8. M1 规模验收

M1 总验收使用 `append_many` 在一个锁周期内预验证并追加 10,000 个顺序事件，执行一次日志 fsync，再原子更新 branch head。该批处理语义用于导入和重放基准；普通 `append` 仍保持单事件 fsync。

必须证明：

- 10,000 event ID、parent、payload hash 全部可重读验证；
- SQLite 可投影相同 10,000 lineage；
- 删除 SQLite 后重建得到相同逻辑 state hash；
- Snapshot restore 后 event head、event count 和 state hash 一致。
