## 项目施工总纲 v3.0

>
> 目标：把“输入结构化大纲 → 输出百万字级连载长篇”变成一套可以断点、回滚、审计、校准和跨 IDE Agent 执行的本地工程。

## 1. 项目定义

### 1.1 要解决的问题

输入一个遵循固定规格的长篇小说大纲，系统协助生产连载正文，并在百万字规模下持续维护：

- 人物身份、动机、心智、关系与行为逻辑
- 世界规则、地点、道具、势力、资源和权限
- 事件、时间、因果、倒叙和真相揭露
- 伏笔、谜团、承诺、角色目标等未来义务
- 意图账本与正文实况账本
- 角色知识边界与读者知识状态
- 多线剧情、钩子、节奏、升级曲线和商业指标
- 版本、分支、回滚、重产、审计证据和生产进度

### 1.2 产品形态

这不是 SaaS，也不是一个必须拥有 API Key 的 Python 服务。

它是一个可以放进本地 IDE Agent 工作区的**可执行工程协议**：

```text
项目文件
+ 确定性 Python 内核
+ .agents/skills 技能包
+ IDE 薄适配层
+ workspace/<book> 数据
+ 结构化产物与退出码
= 本地小说生产操作系统
```

主要目标工具：Antigravity。

兼容目标：Claude Code、Cursor、Codex。

### 1.3 核心分工

```text
文学判断、创意、叙事、正文       → IDE Agent / 可替换模型
事实、时间、状态、关系、权限       → novel_kernel 确定性内核
生产调度、恢复、上下文装配         → studio.py Harness
质量证明、对抗样本、回归           → verification 层
```

**绝不让模型成为唯一事实来源。**

## 2. 项目目标与非目标

### 2.1 必须达成

1. 无 API Key 时可以完成初始化、导入、校验、状态重建、审计、快照、回滚、导出和测试。
2. 有 IDE 内置 Agent 时可以完成从 ContextPack 到正文候选的完整生产闭环。
3. 任意章节生产都可以中断、恢复、重试、分支和回滚。
4. 所有写入权威状态的动作都有事件、版本、来源和证据。
5. 大纲输入不是自由文本，而是固定的 Outline Package。
6. 章级流程稳定可重复，章内 beat 支持自适应递归分解。
7. 质量闸门可用离线写手、变异器和回归集标定。
8. 核心协议不依赖某一家模型、IDE、MCP 或云服务。
9. 所有硬失败通过非零退出码暴露，不允许静默放行。

### 2.2 明确不做

1. 不在首期训练自己的大语言模型。
2. 不把向量数据库、Neo4j、云 API 设为必需依赖。
3. 不让多个 Agent 通过自由群聊共同决定权威事实。
4. 不做自动替代作者的“无监督无限连载”。
5. 不把全文塞进超大上下文当作一致性方案。
6. 不把文学评分单一化成一个 LLM 分数。
7. 不在未完成内核协议前创建大规模业务代码。

## 3. 五条总原则

### 原则一：权威状态与文学文本分离

正文是证据来源之一，但正文不等于状态库。状态只能通过经过校验的 `state_delta` 更新。

### 原则二：追加优先，重写谨慎

事件、运行记录、事故经验和审计证据默认追加。派生状态可以重建，权威历史不能覆盖删除。

### 原则三：预防与拦截双向接线

生成前给 Agent 下发 directives/context pack；生成后再审计。只审计不预防会造成永久返工。

### 原则四：按风险分配计算

普通 beat 低成本单路；转折、高潮、中部、高熵和高义务密度节点增加审计和候选搜索。

### 原则五：验证必须产生外部证据

“模型说完成”“模型自评很好”“测试脚本执行过”都不等于证明。每个阶段必须留下可以复查的产物。

## 5. 统一工作单元：Task → Run → Artifact → Evidence

所有施工和小说生产都使用同一套工作单元：

```text
Task       要做什么，输入是什么，验收是什么
Run        本次实际执行的唯一 ID
Artifact   产生了哪些文件/状态变更
Evidence   为什么认为它通过
```

### 5.1 Task 必须包含

- `task_id`
- `kind`
- `scope`
- `depends_on`
- `inputs`
- `allowed_writes`
- `forbidden_writes`
- `acceptance`
- `failure_policy`

### 5.2 Run 必须包含

- `run_id`
- `task_id`
- `started_at`
- `ended_at`
- `agent_surface`
- `model_identity`（若有）
- `input_hash`
- `output_hash`
- `status`
- `exit_code`
- `evidence_refs`

### 5.3 完成定义

一个任务只有同时满足以下条件才是 `done`：

```text
产物存在
→ 产物可解析
→ schema 通过
→ 硬不变量通过
→ 输出没有越权写入
→ 证据文件存在
→ 生产清单已更新
→ 事件日志已追加
→ 可从快照恢复
```

## 6. 施工总路线

```text
M0  工程宪法、技术选型、目录与退出码
 ↓
M1  事件日志、对象模型、SQLite 投影、原子写入
 ↓
M2  Outline Package 规格与编译器
 ↓
M3  叙事状态：双时态、未来义务、知识边界、快照
 ↓
M4  生产 Harness：ContextPack、Agent 技能、章/beat 任务图
 ↓
M5  结构化抽取、平账、确定性闸门、独立审计
 ↓
M6  离线写手、变异测试、阈值标定、30 章压测
 ↓
M7  IDE 适配、恢复、分支、导出、人工断点
 ↓
M8  可插拔高级技术：Cartridge、Diffusion Editor、BoN、模型路由
```

**施工顺序不可反转：** M4 之前不能让 Agent 直接生产正文；M5 之前不能把“审计通过”当作可信质量；M6 之前不能声称系统已经可靠。

## 8. 架构变更规则

以后任何新技术都必须回答五个问题：

1. 它解决哪个已测量的失败？
2. 没有它时的基线是什么？
3. 它是否改变权威状态协议？
4. 失败时能否降级到确定性路径？
5. 是否有回归集证明它没有损害旧能力？

不能回答的技术，只能进入 `experiments/`，不得进入核心路径。
